How the Results Are Computed

A detailed, code-verified walkthrough of the Agentic PureCLIP pipeline: what the peak caller produces, what the post-processor does with it, and exactly how every number in the results tables and on the dashboard is calculated.

Every formula and step below was checked against the repository — workflow/Snakefile, workflow/postprocess.py, scorers/run_scorers.py, agent/decisions.py, pipeline/motifs.py.

01 The big picture

The project automatically tunes the parameters of an eCLIP peak caller. An optimizer proposes a parameter set; the pipeline runs the caller and scores the result against biological quality signals; the optimizer reads the score and proposes the next set. Repeat.

① PROPOSEPick parameters

An LLM agent (DeepSeek) or Optuna (Bayesian TPE) chooses a parameter set.

② RUNPureCLIP + post-process

Turn eCLIP reads into a final set of binding sites.

③ SCOREMeasure quality

reproducibility · motif · recall → one composite score in [0,1].

④ DECIDENext parameters

The optimizer reads the composite and loops back to ①.

Why one composite score Any single metric can be gamed. Grade only on reproducibility and the optimizer emits one giant site that trivially overlaps everything; grade only on recall and it calls every nucleotide a site to catch all the real ones. Combining orthogonal signals — plus a penalty when the site count collapses — forces an honest balance. (More in § Composite.)

02 The biology, briefly

You only need three ideas to read the results: what eCLIP data is, what a replicate is, and what reproducibility therefore means.

eCLIP data

eCLIP maps where an RNA-binding protein (RBP) touches RNA inside living cells. UV light crosslinks the protein to its RNA; the protein is pulled down with a specific antibody; during sequencing, reverse transcription stops at the crosslink, so the read's 5′ end marks the contact point at near-nucleotide resolution. We start from pre-aligned, deduplicated ENCODE BAM files.

Replicates & reproducibility

What is a replicate?

An IP replicate is an independent repeat of the exact same lab experiment — a separate batch of cells run through the whole eCLIP protocol. Any single run contains false positives from biological noise and the sequencing machine. But genuine RBP binding is biologically driven and recurs in every replicate; random noise usually appears in only one. Two replicates are standard.

What does reproducibility measure?

How consistently the computational tool found the same binding sites across the independent replicates. A site present in only one replicate is treated as likely noise. Crucially, the score is corrected for chance so it can't be inflated by emitting a few broad blobs that overlap by accident — see § Reproducibility.

03 The pipeline, stage by stage

One iteration = one full run of this Snakemake workflow (workflow/Snakefile). Five rules turn two IP BAM files into one scored report.

RULE 1merge_ip

samtools merge combines the two IP replicate BAMs into one merged_ip.bam.

RULE 2pureclip

Run pureclip2 on the merged BAM → crosslink sites + binding regions.

RULE 3pureclip_per_replicate

Run pureclip2 on each replicate separately → per-replicate regions (for reproducibility).

RULE 4postprocess

Filter & normalise the merged regions → the final binding-site set.

RULE 5score

Compute all metrics → score_report.json.

Fast mode When learn_on_chr21 is set, PureCLIP is restricted to chromosome 21 (-iv chr21 -chr chr21) — minutes per iteration instead of hours. All batch experiments used this, and the benchmark/recall step is restricted to chr21 to match (otherwise a genome-wide reference would cap recall at ~4.5%).

04 What PureCLIP produces, exactly

PureCLIP is a hidden Markov model over the crosslink-truncation signal. For each BAM it emits two BED files. The exact command (from the Snakefile) is:

pureclip2 -i merged_ip.bam -bai … -g genome.fa -nt N -bw bandwidth_nt -dm merge_distance_nt [-ld] [-iv chr21 -chr chr21] -o crosslink_sites.bed -or binding_regions.bed
① crosslink_sites.bed (-o)

Individual single-nucleotide crosslink sites — the HMM's per-base calls of where the protein contacted the RNA, each with a score.

② binding_regions.bed (-or)

Nearby crosslink sites merged into binding regions. Each region's name column holds the list of contributing crosslink positions (;-separated) — the post-processor counts these. This is the file post-processing consumes.

Three parameters shape these outputs directly:

  • bandwidth_nt (-bw) — the smoothing window when scanning read coverage. Larger → broader, more sensitive regions; smaller → sharper, more precise calls.
  • merge_distance_nt (-dm) — how close two crosslink sites must be to be merged into one region.
  • high_precision_mode (-ld) — PureCLIP's stricter calling mode: fewer but higher-confidence sites.

Rule 3 runs the identical caller on each IP replicate on its own, producing ip_rep1/pureclip_regions.bed and ip_rep2/pureclip_regions.bed. These are never post-processed — they exist only so the scorer can ask "does each final site also appear in each replicate?" (reproducibility).

05 What post-processing does

The post-processor (workflow/postprocess.py) turns PureCLIP's raw binding_regions.bed into the final, uniform binding-site set. Three steps:

  1. Length filter. Drop any region shorter than min_region_length_nt (fixed at 3 nt).
  2. Event filter. Count the crosslink positions in each region's name field (the ;-separated list) and drop regions with fewer than min_crosslink_events. This is the main sensitivity knob — higher = fewer, stronger sites.
  3. Footprint normalisation. For every surviving region, take its midpoint (summit) and emit a fixed-width interval of exactly force_width nt centred there. Every final site is the same width — roughly the protein's ~9 nt RNA footprint.
summit = (region.start + region.end) // 2 final_site = [ summit − force_width//2 , summit − force_width//2 + force_width ]

The result is written to binding_sites.reproducible.bed — the Sites column in every results table is simply the number of rows in this file.

Naming gotcha (verified in code) Despite the filename, this set is not filtered for reproducibility. Post-processing only applies the length, event-count, and width steps above; it never intersects with the per-replicate calls. Reproducibility is measured later by the scorer, not enforced here. So "reproducible.bed" is a legacy name — read it as "the final binding sites."

06 How the five metrics are computed

The scorer (scorers/run_scorers.py) writes score_report.json. Below is exactly what each reported value means and how it is calculated — verified against the code. Bed intersections use bedtools.

Sitescount n_binding_sites
What it means
The number of final, filtered binding sites for this parameter run.
How it's calculated
The row count of binding_sites.reproducible.bed — i.e. the regions that survived the length and crosslink-event filters, normalised to force_width. Watch this number: a high quality score on very few sites is a collapse, not a win.
Reproducibilityweight ×0.50 0 – 1reproducibility_score
What it means
The fraction of final binding sites that appear in every individual replicate — corrected for random chance.
How it's calculated — step by step
  1. Observed agreement. Start from the final sites and chain bedtools intersect -u against replicate 1's regions, then replicate 2's, and so on. What survives overlaps all replicates. observed = survivors / total sites.
  2. Chance baseline. Broad intervals overlap by geometry alone, so the sites are randomly repositioned with bedtools shuffle (each interval kept on its own chromosome) and the agreement is re-measured. This is repeated 3 times; expected = the mean.
  3. Chance-corrected score.
reproducibility_score = clamp( observed − expected1 − expected , 0, 1)

Also reported: reproducibility_enrichment = observed / expected (>1 means real agreement above chance). This construction is why the metric can't be gamed by collapsing to a few broad, trivially-overlapping sites — those score high on observed but equally high on expected, cancelling out.

Motifweight ×0.25 0 – 1motif_hit_rate
What it means
The fraction of binding sites whose sequence contains the RNA "word" the target protein is known to bind.
How it's calculated
  1. Each site is padded by ±15 nt and its sequence is pulled from the genome with bedtools getfasta -s (strand-aware).
  2. Each window is scored with a Position Weight Matrix (PWM) (log-odds) from motif databases (mCrossBase, ATtRACT, CISBP-RNA, …). A window "hits" if its best log-odds score clears the 80% threshold — defined robustly as 80% of the way from the PWM's minimum to maximum possible score, not a fraction of the max.
  3. To make it biologically meaningful, the foreground hit rate is divided by a background hit rate from composition-matched shuffled windows (each window's own letters shuffled) → enrichment.
  4. Many motifs are scored; the reported motif_hit_rate is the foreground rate of the most enriched motif — so one common-but-uninformative motif can't dominate the headline.

motif_enrichment (the "×N" you see next to it) is that best motif's foreground/background ratio. If no PWM is available, the scorer falls back to an IUPAC consensus regex (e.g. UGCAUG).

Recallweight ×0.25 0 – 1benchmark_region_recall
What it means
How many of the known, ground-truth binding regions the pipeline recovered.
How it's calculated
ENCODE provides a curated, high-confidence set of reference regions for each protein. Recall = the fraction of those reference regions that overlap at least one of our called sites:
benchmark_region_recall = # reference regions hit by ≥1 sitetotal reference regions

Computed as bedtools intersect -a reference -b sites -u. Under chr21 fast mode the reference is first restricted to chr21 for a fair denominator. The mirror quantity benchmark_region_overlap (fraction of our sites that hit a reference — a precision-like measure) is also reported but not part of the composite.

Composite0 – 1 composite
What it means
The single source-of-truth score the optimizers climb. A weighted blend of the three signals, multiplied by a collapse guard (yield factor) that drives the score toward zero below 10 sites.
How it's calculated (agent/decisions.py)
composite = ( 0.5·reproducibility + 0.25·motif + 0.25·recall ) × min(1, n_binding_sites / 10)
  • Weights renormalise over whichever terms are present in a report (so a missing term doesn't zero the score).
  • Collapse guard = min(1, n/10): full credit at ≥10 sites, ramping linearly to 0 at zero sites. With only a handful of sites, reproducibility and motif trivially hit 1.0 — this guard makes that degenerate "win" score near zero.
Single source of truth The dashboard imports this exact function and recomputes the composite live from each score_report.json. So the dashboard can never disagree with the optimizer, and changing the objective re-scores all historical runs automatically.

07 The parameters being tuned

Seven knobs, each with fixed search bounds (pipeline/configs.py). The optimizer may only propose integer/boolean values inside these ranges.

ParameterRangeStageEffect
bandwidth_nt20–100PureCLIPSmoothing window. Larger → broader/more sites; smaller → sharper.
merge_distance_nt4–16PureCLIPHow close two crosslink sites merge into one region.
high_precision_mode0 / 1PureCLIPStricter calling (-ld): fewer, higher-confidence sites.
use_input_covariate0 / 1PureCLIP*Use the SMInput control to subtract background. *See note.
min_crosslink_events2–6Post-procMin crosslink events to keep a site. Higher → fewer, stronger sites.
force_width3–15Post-procFixed width every site is normalised to (~9 nt footprint).
cluster_gap_width4–16Post-proc*Intended max gap when clustering sites into regions. *See note.
Implementation note (verified in code) Two knobs are in the search space and get proposed by the optimizers, but are not currently wired into the executed workflow: cluster_gap_width is never read by postprocess.py or the Snakefile, and use_input_covariate is carried in the config/snapshot but the pureclip2 command line does not pass an input-covariate flag. In the runs analysed, pipeline behaviour is therefore driven by the other five parameters (bandwidth_nt, merge_distance_nt, high_precision_mode, min_crosslink_events, force_width). Worth confirming before reading too much into any tuned value of those two.

The loop beats hand-set defaults on every dataset. Honest head-to-head: LLM 3 : Optuna 2 — the LLM sweeps the harder K562 cell line and never collapsed a run; Optuna wins both HepG2 datasets and found the single best legitimate config.

The "0.775" trap — a scoring lesson The highest number in the raw logs is 0.775 (QKI_K562, Optuna). It is not a win: that run had reproducibility 1.0, motif 1.0, and n = 1 site. One site trivially agrees with itself and sits on a motif. The value was logged as the raw weighted blend before the collapse guard; with the guard applied — × min(1, 1/10) — the honest score is ≈ 0.078, which is exactly what the live dashboard shows (it recomputes with the guard). This is the whole reason the collapse guard exists, and why you always read a score next to its site count. Two more inflated scores fail the same way (QKI_HepG2 @ n=6, PUM1 @ n=9) — all Optuna, none LLM.
