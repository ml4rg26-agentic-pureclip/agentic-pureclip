# Configuration reference

The files in this directory describe datasets, individual PureCLIP evaluations,
and multi-job optimization batches. Paths are resolved from the repository root,
so run all commands from there.

## Choose the right configuration type

| Configuration | Consumer | Purpose |
|---|---|---|
| `run_config.yaml` | LLM graph, Optuna runner, and Snakemake | Active configuration for a direct optimization or workflow run |
| `datasets/*.yaml` | Direct runs and human review | Materialized configuration for one registered dataset |
| YAML with `defaults:` and `jobs:` | `scripts/run/overnight_batch.py` | Current failure-tolerant batch format; supports multiple datasets, optimizers, and experimental arms |
| YAML with `runs:` | `scripts/run/batch_runner.py` | Simpler LLM-only batch format; supports optional local parallelism |
| `priors.json` | LLM/report fallback | Fallback biology context when an active run config has no embedded `priors` section |
| `best_config.yaml` | Written by the LLM and Optuna loops | Convenience snapshot of the latest best configuration; last writer wins |

The two batch formats are not interchangeable. For new supervised runner jobs,
prefer the failure-tolerant `defaults`/`jobs` format and follow the
[VM batch runbook](../docs/deploy-a-new-batch-job.md).

## Sources of truth and generated files

- [`pipeline/datasets.py`](../src/agentic_pureclip/pipeline/datasets.py) is the
  dataset registry and defines the standard input paths and starting values.
- [`pipeline/configs.py`](../src/agentic_pureclip/pipeline/configs.py) validates
  active run configs and defines the hard default search bounds.
- `datasets/*.yaml` are materialized snapshots. Regenerate one after changing
  the registry rather than maintaining two divergent definitions.
- `run_config.yaml` is mutable during a direct optimization because the loop
  persists each candidate configuration to `CONFIG_PATH`.
- `config/ui_runs/` is an ignored runtime directory created by the CLI.
  `config/batch/` is also generated by a runner but is not currently covered by
  `.gitignore`; do not commit it.
- `best_config.yaml` is shared by all direct optimizer processes. Use the
  per-job configuration and history under `results/` for durable provenance.

Generate or refresh a dataset config with:

```bash
uv run python scripts/data/write_dataset_config.py HNRNPK_K562
```

## Active run configuration

An active run config is selected through `CONFIG_PATH`; the default is
`config/run_config.yaml`. The validator requires the following core structure.

| Section | Required content |
|---|---|
| Top level | Non-empty `run_id` and `target_protein` |
| `samples.ip` | At least two replicates, each with a `bam` path |
| `samples.input_control` | At least one control replicate with a `bam` path |
| `reference` | `genome_fasta`; `annotation_gtf` is optional |
| `pureclip` | `bandwidth_nt`, `merge_distance_nt`, `high_precision_mode`, and `use_input_covariate` |
| `postprocessing` | `force_width`, `min_region_length_nt`, and `min_crosslink_events` |
| `resources` | Positive integer `threads` |

Common optional sections are:

- `dataset_id`, `cell_line`, and `clip_protocol`: experiment metadata.
- `priors`: target protein, motifs, protocol, expected footprint, and objective
  weights used by the LLM and scorers.
- `benchmark`: optional BED and summary files for reference-overlap metrics.
- `reproducibility`: thresholds used by reproducibility scoring.
- `output`: result placement. `results_dir` is the current workflow output;
  optimizers may combine `results_root` with `use_run_id_subdir` to isolate
  iterations.
- `search_bounds`: the parameters optimized in this run. If absent, the hard
  defaults below are used.

### PureCLIP and post-processing fields

| Field | Meaning |
|---|---|
| `pureclip.bandwidth_nt` | KDE smoothing bandwidth |
| `pureclip.merge_distance_nt` | Maximum gap used to merge neighboring crosslink sites |
| `pureclip.high_precision_mode` | Enables PureCLIP high-precision mode |
| `pureclip.use_input_covariate` | Uses the input-control BAM as a covariate |
| `pureclip.learn_on_chr21` | Restricts learning/calling to chromosome 21 when true |
| `pureclip.use_cl_motif_covariate` | Enables an optional crosslink motif covariate |
| `pureclip.cl_motif_file` | Optional motif-covariate file |
| `postprocessing.min_crosslink_events` | Minimum crosslink events required to retain a region |
| `postprocessing.min_region_length_nt` | Minimum retained region length; static by default |
| `postprocessing.cluster_gap_width` | Gap used when clustering nearby calls |
| `postprocessing.force_width` | Fixed width of the final centered footprint |

### Default optimization bounds

These bounds come from `DEFAULT_SEARCH_BOUNDS` and apply to both optimizers when
the active config does not provide narrower `search_bounds`.

| Parameter | Default range |
|---|---:|
| `pureclip.merge_distance_nt` | 4–16 |
| `pureclip.bandwidth_nt` | 20–100 |
| `pureclip.high_precision_mode` | 0–1 |
| `pureclip.use_input_covariate` | 0–1 |
| `postprocessing.min_crosslink_events` | 2–6 |
| `postprocessing.force_width` | 3–15 |
| `postprocessing.cluster_gap_width` | 4–16 |

Boolean parameters use `0:1` in search bounds and are converted back to booleans
in the materialized run config. Starting values are clamped into custom bounds
by the failure-tolerant batch runner.

## Failure-tolerant batch manifests (`defaults` / `jobs`)

This is the current format used by `scripts/run/overnight_batch.py`, the
dashboard-generated CLI command, and the documented VM workflow.

```yaml
defaults:
  max_iter: 8
  threads: 32
  learn_on_chr21: true
  per_job_timeout_min: 240
  optimizer: optuna
  objective_weights: {reproducibility: 0.5, motif: 0.25, recall: 0.25}
  search_bounds:
    pureclip:
      bandwidth_nt: [20, 100]

jobs:
  - {id: hnrnpk_optuna, dataset: HNRNPK_K562}
  - {id: qki_llm, dataset: QKI_K562, optimizer: llm, max_iter: 8}
```

`defaults` apply to every job. A job may override `max_iter`, `threads`,
`learn_on_chr21`, `optimizer`, `pureclip`, `postprocessing`,
`objective_weights`, or `search_bounds`. Set `no_priors: true` on an LLM job for
the prior-ablation arm. `per_job_timeout_min` is the batch-wide per-job cap and
belongs under `defaults`.

Representative manifests:

- [`smoke_final_jobs.yaml`](smoke_final_jobs.yaml): small multi-job validation.
- [`final_results_jobs.yaml`](final_results_jobs.yaml): LLM, Optuna, and
  no-priors arms across several datasets.
- [`fullgenome_rbfox2_k562.yaml`](fullgenome_rbfox2_k562.yaml): full-genome run
  with pinned single-value bounds.

Validate and launch these manifests with the
[VM batch runbook](../docs/deploy-a-new-batch-job.md).

## Simple batch manifests (`runs`)

`scripts/run/batch_runner.py` reads the older, smaller `runs` schema:

```yaml
runs:
  - id: quick_hnrnpk_k562
    dataset: HNRNPK_K562
    chr21_only: true
    max_iter: 4
    threads: 8
```

This runner starts the LLM graph only and writes to `results/batch/`. It does
not support the `defaults`/`jobs` optimizer and arm fields. Use it only when
that simpler behavior is intentional.

```bash
uv run python scripts/run/batch_runner.py \
  --manifest config/batch_runs.yaml --dry-run
```

## Priors, weights, and fallback behavior

Dataset configs normally embed `priors`, including motifs resolved from the
available motif databases. Embedded priors take precedence. `priors.json` is a
fallback for direct LLM/report execution when an active config has no `priors`
section; it is not the primary per-dataset registry.

Objective weights live at `priors.objective_weights` in an active run config.
The batch runner accepts `objective_weights` in its manifest and injects them
into that location. Defaults are reproducibility `0.5`, motif `0.25`, and recall
`0.25`; the objective renormalizes over available components.

## Validation checklist

Before committing or launching a configuration:

1. Confirm all paths are relative to the repository root and do not contain
   credentials.
2. Regenerate materialized dataset YAML after registry changes.
3. Ensure the starting tunable values fall inside custom `search_bounds`.
4. Dry-run the selected batch runner and confirm every dataset reports
   `data=OK` on the VM.
5. Keep downloaded data, references, generated manifests, and results out of
   Git.
